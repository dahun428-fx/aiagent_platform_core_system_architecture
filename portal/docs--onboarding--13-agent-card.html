Agent Card와 Agent 간 통신

개발자 가이드 문서입니다. 규범은 Agent Card 기술 표준 문서와 A2A 1.0.0 명세가 기준입니다.

주요 용어 Agent Card A2A 확장 Agent Card JWS · JCS Registry

학습 목표

  • A2A Agent Card의 필수·선택 필드를 설명할 수 있습니다.
  • 공개 카드와 인증된 확장 카드의 차이를 설명할 수 있습니다.
  • Agent Card의 서명과 검증 절차를 설명할 수 있습니다.
  • Registry가 Agent Card를 발행하는 규칙을 설명할 수 있습니다.

배경

문제 정의 다른 팀의 Agent를 호출하려면, 그 Agent가 무엇을 할 수 있고 어디로 어떻게 인증해 호출하는지 알아야 합니다.

현황 Agent 정보를 팀마다 문서나 메신저로 공유하면 최신 상태를 보장할 수 없고, 정보가 위조되었는지도 확인할 수 없습니다.

설계 방향 Registry가 Manifest와 등록 정보로 A2A Agent Card를 생성하고 조직 키로 서명해 발행합니다. 호출하는 쪽은 서명을 검증한 카드만 신뢰합니다.

Agent 간 통신의 두 계층

계층 기준 역할
발견(discovery) A2A 1.0.0 Agent Card Agent의 기능, 접속 인터페이스, 인증 방식을 알림
호출 공통 Agent 통신 계약(cross-agent.schema.json) 상위 호출 ID, 축소된 권한 범위, 호출 깊이·예산 전달

A2A 프로토콜로 호출하는 것은 선택 사항입니다. 발견은 Agent Card로 통일합니다.

Agent Card 필드 (A2A 1.0.0)

필드 필수 내용
name, description, version 필수 Agent 이름, 목적, 버전
supportedInterfaces 필수 접속 인터페이스 목록. 첫 항목이 우선입니다
capabilities 필수 streaming, pushNotifications, extensions, extendedAgentCard
defaultInputModes, defaultOutputModes 필수 입출력 미디어 유형
skills 필수 Agent 기능 목록
provider 선택 organization, url
securitySchemes, securityRequirements 선택 인증 방식과 요구 조건
signatures 선택 JWS 서명
documentationUrl, iconUrl 선택 문서·아이콘
AgentInterface

url(HTTP는 HTTPS, gRPC는 host:port), protocolBinding(JSONRPC·GRPC·HTTP+JSON), protocolVersion, 선택 tenant. tenant가 있으면 클라이언트는 모든 요청에 그 값을 그대로 넣습니다.

AgentSkill

필수 id, name, description, tags. 선택 examples, inputModes, outputModes, skill별 securityRequirements.

SecurityScheme

API key, HTTP auth, OAuth 2.0, OpenID Connect, mTLS 중 정확히 하나입니다. OAuth 2.0은 Implicit·Password flow를 지원하지 않습니다.

명세 표기 차이 A2A 1.0.0 명세는 필드 표에서 securityRequirements, 본문 일부에서 AgentCard.security로 표기합니다. 구현은 규범 원본인 spec/a2a.proto의 정의를 따릅니다.

공개 카드와 확장 카드

공개 카드에 두지 않는 정보

  • 사내 Agent의 내부 URL
  • 민감한 skill 설명
  • 시크릿·토큰 등 정적 자격증명

플랫폼의 공개 범위

  • 사내 Agent: 공개 /.well-known/agent-card.json 없음, 인증된 Registry 조회로만 제공
  • 외부 공개 Agent: https://{domain}/.well-known/agent-card.json에 최소 정보
  • 상세 정보: 인증된 확장 카드로만 제공
  1. 공개 카드 조회capabilities.extendedAgentCard: true 확인
  2. 인증공개 카드에 선언된 인증 방식으로 토큰 획득
  3. GetExtendedAgentCard인증 수준에 따라 다른 내용 반환
  4. 카드 교체세션 동안 공개 카드 대신 사용

확장 카드는 반드시 인증을 요구하며(MUST), 확장 카드에도 유출 시 악용될 수 있는 정보는 넣지 않습니다(SHOULD NOT). 플랫폼은 확장 카드의 내용을 권한 교집합에 따라 제한합니다.

서명과 검증

  1. 정규화signatures 제외 후 JCS(RFC 8785) 정규화
  2. 서명JWS(RFC 7515), 보호 헤더 alg·typ·kid, 선택 jku
  3. 발행Registry가 조직 키로 서명한 카드 제공
  4. 검증키 조회(kid·jku) → 정규화 → 서명 검증 후 신뢰
{"alg": "ES256", "typ": "JOSE", "kid": "key-1", "jku": "https://example.com/agent/jwks.json"}
  • 소비 측은 서명을 검증한 카드만 신뢰합니다(MUST). 키는 HTTPS로 받거나 신뢰 키 저장소를 사용합니다.
  • 만료·폐기된 키는 사용하지 않습니다(MUST NOT). 키 교체 기간에는 서명을 여러 개 둘 수 있습니다.
  • 서명이 유효하더라도 카드 내용(skill 설명 등)은 비신뢰 데이터입니다. 카드 내용으로 권한 정책을 변경할 수 없습니다.

Registry의 발행 규칙

규칙 내용
생성 Registry가 Manifest와 등록 정보에서 생성합니다. 수동 작성 카드는 받지 않습니다
필드 대응 metadata.name·version → name·version, 기능 선언 → skills, identity.requiredScopes → 보안 요구, 승인된 실행 환경 endpoint → supportedInterfaces, metadata.owner.team → provider.organization
상태 연동 production-approved 버전만 발행하고, deprecated·quarantined·retired 전환 시 갱신·회수합니다
캐시 Cache-Control과 카드 version 또는 내용 해시 기반 ETag를 제공합니다
버전 A2A 1.0.0을 기준으로 하며 A2A-Version 헤더를 사용합니다
조회 API A2A는 레지스트리 API를 표준으로 정하지 않으므로 Agent Platform APIs에 Registry 조회 API를 정의합니다

제공 범위

v0.1은 Agent Card 발행·소비 규칙을 정의합니다. 카드 생성·서명 구현, Registry 조회 API 계약, A2A 프로토콜 adapter는 후속 단계로 제공합니다.

이해도 점검

Q1. 사내 전용 Agent의 Agent Card는 어디에서 조회합니까?

공개 /.well-known/agent-card.json이 아니라, Agent Platform APIs의 인증된 Registry 조회로만 조회합니다.

Q2. 서명 검증 전에 수행해야 하는 정규화 방식은 무엇입니까?

signatures 필드를 제외하고 JCS(RFC 8785)로 정규화합니다.

Q3. Agent Card는 어떤 상태의 Agent 버전에 발행됩니까?

production-approved 상태의 버전에만 발행합니다.

요약

  • Agent 발견은 A2A 1.0.0 Agent Card, 호출은 공통 Agent 통신 계약을 따릅니다.
  • 사내 Agent는 인증된 Registry 조회로만 카드를 제공하고, 상세 정보는 확장 카드로 제한합니다.
  • Registry가 JCS 정규화 후 JWS로 서명하며, 소비 측은 서명을 검증한 카드만 신뢰합니다.

근거와 참고 자료

  • 서명·정규화 규격: IETF·OAuth
