Agent Identity

개발자 가이드 문서입니다. 규범은 Agent Identity, 보안 경계 기술 표준 문서가 기준입니다.

  1. ①부른다
  2. ②어떻게 여기 있나
  3. ③실행된다
  4. ④ERP를 읽고 메일을 보내려 한다
  5. ⑤누구 권한으로
  6. ⑥모델에 묻는다
  7. ⑦함정을 만난다
  8. ⑧답이 틀렸다
  9. ⑨점수를 매긴다
  10. ⑩고쳐서 다시 올린다
  11. ⑪어디서 이 일을 하나

지금까지 서연이 부른 invoice-summary가 tool-erp-read로 청구서를 읽었습니다. 메일 보내기(요청 C)는 다른 Agent invoice-mailer가 맡고, 지훈의 승인을 기다립니다.

장면

같은 날 인턴 하준이 서연과 똑같은 문장으로 invoice-summary를 부릅니다. 서연은 요약을 받았는데 하준은 403을 받습니다. Agent도 질문도 같고 부른 사람만 다릅니다. 하준에게는 Agent를 부를 권한만 있고 모델과 ERP 읽기 권한이 없습니다. Agent는 자기 권한이 아니라 부른 사람의 권한 안에서 일하기 때문에 이런 차이가 납니다.

Agent Identity가 없다면 Agent를 부를 수 있는 사람은 누구나 Agent가 닿는 모든 데이터를 볼 수 있게 됩니다.

무슨 일이 일어나나

  1. 1. 부른 사람의 권한을 확인한다토큰 → 테넌트 · scope
  2. 2. Agent가 요구하는 권한과 맞춰 본다requiredScopes
  3. 3. 도구를 부를 때 한 번 더 본다도구 목록 · 실행 중 권한
  4. 4. 잠깐 쓰는 출입증으로 들어간다lease

실물 보기

요청 A가 지나는 관문을 서연과 하준의 값으로 채운 표입니다.

예시

관문 보는 것 서연 하준
테넌트 본문에 적은 테넌트가 토큰의 테넌트와 같은가 통과 통과
진입 Manifest requiredScopes 세 개가 모두 호출자 권한과 정책이 겹치는 범위에 있는가 통과 403. models.invoke와 tools.read가 없음. 코드가 실행되지 않음
도구 목록 부르려는 도구가 Manifest capabilities.tools에 있는가 tool-erp-read 통과 여기까지 오지 않음
실행 중 권한 겹치는 범위에 도구가 요구하는 scope가 있는가 tools.read 통과 여기까지 오지 않음
  • 서연의 권한은 agents.invoke, models.invoke, tools.read, tools.write이고, 하준의 권한은 agents.invoke 하나입니다.
  • "겹치는 범위"는 호출자가 가진 권한이면서 회사 정책도 허용한 권한을 말합니다. 서연이 권한을 가졌어도 정책이 막으면 없는 것과 같습니다.
  • 앞 관문에서 막히면 뒤 관문은 보지 않으므로, 403이 나면 위에서부터 확인합니다.

마지막 관문에서 쓰는 출입증(lease)입니다. 저장소 fixture examples/fixtures/credential-lease.json입니다.

실행 결과 · 내 PC의 로컬 mock

{
  "credentialRef": "lease-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "audience": "tool-search",
  "scopes": ["tools.read"],
  "expiresAt": "2099-01-01T00:00:00Z",
  "nonExportable": true
}
  • credentialRef: 비밀번호가 아니라 번호표여서, 이 값을 알아도 ERP에 직접 들어갈 수 없습니다.
  • audience와 scopes: 이 출입증을 쓸 수 있는 도구와 권한입니다. 다른 도구에는 쓸 수 없습니다.
  • expiresAt: 만료 시각입니다. fixture는 형식 검증용이라 먼 날짜가 적혀 있지만, 로컬 mock이 실제로 발급하는 lease는 60초 뒤 만료되고 한 번 쓰면 다시 쓸 수 없습니다.
  • nonExportable: Agent 코드와 모델에게 넘어가지 않는다는 표시입니다. 실제 자격증명으로 바꾸는 일은 신뢰 경계 안쪽에서만 일어납니다.
더 보기: 요청 C의 관문, 그리고 "만약에" 다섯 가지

요청 C(invoice-mailer, 메일을 보냄)를 서연이 보낼 때입니다. tools.write라는 이름과 쓰기 승인은 로컬 mock에 없고 참조 구현의 S6a 시나리오에 있으므로 이 표는 예시입니다.

관문 보는 것 서연
진입 requiredScopes 네 개(tools.write 포함) 통과
도구 목록 tool-mail-send가 capabilities.tools에 있는가 통과
실행 중 권한 겹치는 범위에 tools.write가 있는가 통과
쓰기 승인 이 요청에 묶인 유효한 승인이 있는가 지훈이 승인하기 전에는 실행이 멈춰 기다림. 승인 없는 호출이 도구 경로에 닿으면 앱은 403 Policy denied
  • 회사 정책이 이 테넌트의 tools.read를 막았다면 서연이 권한을 가졌어도 진입 관문에서 403입니다.
  • 민준이 requiredScopes에서 tools.read를 빠뜨렸다면 tools.read가 없는 사용자도 진입을 통과하고, 코드가 도구를 부르는 순간 실행 중 권한 관문에서 403이 납니다. 그래서 도구가 요구하는 scope를 requiredScopes에 모두 적어 일찍 막습니다.
  • 서연에게 tools.write가 없었다면 요청 A는 그대로 되고, 요청 C는 진입 관문에서 403이라 invoice-mailer의 코드가 실행되지 않습니다.
  • invoice-summary가 tool-mail-send를 부르려 하면 서연의 권한과 상관없이 도구 목록 관문에서 403입니다.
  • 신원 모드가 independent라면 실행 중 권한은 호출자가 아니라 Manifest 선언과 정책이 겹치는 범위로 정해지고, 사용자의 신원은 실리지 않습니다. 사용자가 없는 예약 작업에 씁니다.

작은 사례 expense-settlement(출장 정산 Agent)가 invoice-summary를 부를 때, 하위 Agent에 넘어가는 권한은 상위 Agent가 가진 권한을 넘을 수 없습니다. Agent를 여러 번 거쳐도 권한은 줄어들 뿐 늘지 않습니다.

직접 해 보기

  1. "하준의 권한으로"를 눌러 보세요. 하준이 통과하려면 무엇이 필요한가요.
  2. 서연의 tools.write를 끄면 요청 A와 요청 C는 각각 어디까지 가나요.
  3. Manifest의 requiredScopes에서 tools.read를 빠뜨리고 호출자의 tools.read를 꺼 보세요. 어느 관문에서 막히나요.

잘못되면

하준이 invoice-summary를 부르면 403을 받습니다. 로컬 mock의 응답 본문에는 Caller lacks a scope required by the Agent Manifest라고 적혀 있습니다. Agent 코드는 한 줄도 실행되지 않았습니다. 이 실패는 코드가 아니라 권한을 고쳐야 풀립니다. 하준에게 필요한 권한을 주거나, 하준이 이 Agent를 부르지 않게 합니다.

민준이 테스트하면서 요청 본문에 다른 팀의 테넌트를 적으면 403 Tenant assertion does not match authenticated identity를 받습니다. 테넌트는 토큰에서만 정해지고 본문의 값은 비교에만 쓰이므로, 본문을 바꿔 다른 팀의 데이터에 닿는 길은 없습니다.

더 보기: 만료된 lease, 그리고 내부 구간의 거절

만료됐거나 이미 쓴 lease를 다시 쓰면 로컬 mock은 403 Credential lease binding or expiry denied로 거절합니다. lease는 발급받은 workload, 호출 번호, 대상 도구에 묶여 있어 다른 호출이 주워 써도 통하지 않습니다.

아래는 앱이 보는 값이 아니라 참조 구현의 모델 경로를 직접 호출했을 때의 값입니다.

실행 결과 · 내부 진단 · 내부 경로를 직접 호출한 값

상황 모델 경로의 응답 시나리오
내부 신원의 테넌트가 정책의 테넌트와 다름 403 Policy denied S1 tenant-mismatch
서명한 뒤 내용이 바뀜 403 Internal signature missing or invalid S1 tampered
필요한 scope가 없음 403 Policy denied S1 missing-scope

정문을 지났다고 해서 안쪽 구간이 서로를 그냥 믿지는 않고, 구간마다 신원과 서명을 다시 확인합니다.

내가 할 일

  1. 신원 모드를 고릅니다. 사용자를 대신해 일하면 delegated, 예약 작업처럼 사용자가 없으면 independent입니다.
  2. Manifest identity.requiredScopes에 Agent가 쓰는 모델과 도구의 scope를 모두 적습니다.
  3. 코드에 자격증명을 넣지 않습니다. 애초에 넣을 자리도 없습니다.
  4. 403이 나면 관문을 위에서부터 확인합니다. 테넌트, 진입, 도구 목록, 실행 중 권한 순서입니다.

내 PC에서 해 보기 적합성 검사의 C4(테넌트 위조), C10(Manifest requiredScopes), C11(identity.mode)이 이 장의 관문을 실제로 확인합니다. 출력 11줄 가운데 세 줄입니다.

python scripts/agentctl.py conformance examples/agents/invoice-summary

규칙으로 정리

  • 신원과 테넌트는 검증된 토큰에서만 정합니다. 요청 본문의 값으로 권한을 주지 않습니다(MUST NOT). 장면 ⑤
  • 실행 중 권한은 사용자 권한 ∩ Agent 권한 ∩ 도구 허용 범위 ∩ 정책을 넘을 수 없습니다(MUST). 장면 ⑤
  • 사람의 신원, Agent workload의 신원, 바깥 시스템에 위임받은 자격증명은 서로 다른 것으로 다룹니다.
  • 자격증명 원문은 Runtime과 모델에 넘기지 않습니다. 금방 만료되고, 그 호출에만 묶여 있고, 밖으로 내보낼 수 없는 lease만 씁니다(MUST).
  • 토큰을 받은 그대로 다음 시스템에 넘기지 않습니다(token passthrough 금지). 대상(audience)이 정해진 토큰만 씁니다.

한 문장으로

Agent가 할 수 있는 일은 부른 사람이 할 수 있는 일을 넘지 못합니다.

이해 점검

Q1. 같은 Agent인데 왜 서연은 되고 하준은 안 되나요?

Agent의 Manifest가 요구하는 권한 세 개를 서연은 모두 갖고 있고 하준은 하나만 갖고 있기 때문입니다. Agent는 부른 사람의 권한 안에서만 일합니다.

Q2. 403을 받았습니다. 어느 관문부터 확인하나요?

위에서부터 테넌트, 진입(requiredScopes), 도구 목록, 실행 중 권한 순서로 확인합니다. 앞에서 막히면 뒤는 검사하지 않기 때문입니다.

Q3. 민준이 requiredScopes에 tools.read를 적지 않았습니다. tools.read가 없는 사용자가 부르면 어떻게 되나요?

진입 관문은 통과하고 코드가 실행되지만, 도구를 부르는 순간 실행 중 권한 관문에서 403이 납니다. 미리 적어 두면 코드가 실행되기 전에 막힙니다.
