Agent Evaluation

개발자 가이드 문서입니다. 규범은 평가 기술 표준 문서가 기준입니다.

  1. ①부른다
  2. ②어떻게 여기 있나
  3. ③실행된다
  4. ④ERP를 읽고 메일을 보내려 한다
  5. ⑤누구 권한으로
  6. ⑥모델에 묻는다
  7. ⑦함정을 만난다
  8. ⑧답이 틀렸다
  9. ⑨점수를 매긴다
  10. ⑩고쳐서 다시 올린다
  11. ⑪어디서 이 일을 하나

지금까지 서연이 "한빛상사 10월 청구서"를 물었더니 금액이 틀렸습니다. 민준이 추적 기록을 보니 오류는 없었고, 개발 환경에서 다시 실행해 보고서야 조회할 때 월이 빠진 것을 찾았습니다.

장면

민준은 이상했습니다. 시험에서 만점을 받고 승인된 invoice-summary 1.2.0이 틀렸기 때문입니다. 시험지를 열어 보니 질문 28개가 전부 "청구서 INV-○○○○ 요약해 줘" 형태였습니다. 민준은 서연처럼 거래처명으로 묻는 질문 12개를 시험지에 더하고 같은 버전을 다시 채점했습니다. 기준은 0.90인데 결과는 0.70이었습니다. 시험지에 없던 질문은 한 번도 검사받은 적이 없었던 것입니다.

Agent Evaluation이 없다면 "몇 번 써 보니 잘 되더라"가 배포 기준이 됩니다.

무슨 일이 일어나나

  1. 1. 시험지가 있다평가 데이터셋
    질문 + 정답
  2. 2. Agent가 모두 푼다invoice-summary 1.2.0
  3. 3. 채점기가 견준다지표마다 점수 하나
  4. 4. 기준을 넘어야 올라간다게이트

실물 보기

민준이 추가한 33번째 행입니다. 서연이 운영에서 물었던 바로 그 문장입니다.

예시

{
  "id": "row-33",
  "input": "한빛상사 10월 청구서 요약해 줘",
  "expected": {
    "invoiceId": "INV-2048",
    "amount": 12400000
  },
  "queryHint": "한빛상사 2026-10"
}
  • input: 사용자가 실제로 물은 문장입니다. 운영에서 틀린 요청이 그대로 시험 문제가 됩니다.
  • expected.invoiceId: 금액만이 아니라 어느 청구서를 가져왔어야 하는지도 정답에 넣습니다.
  • queryHint: 조회어는 여러 가지가 정답일 수 있어서 채점에는 쓰지 않고, 틀린 행의 원인을 찾을 때 비교해 봅니다.

1.2.0이 이 행에서 한 일입니다.

예시

{"query": "한빛상사", "invoiceId": "INV-2101", "amount": 9800000}

월이 빠져 11월 청구서를 가져왔으므로 이 행은 오답입니다. 추가한 12행이 모두 틀려 28/40 = 0.70이 됐습니다.

채점이 끝나면 지표 하나에 결과 레코드 하나가 남습니다. 형식은 계약 evaluation.schema.json을 따릅니다.

예시

{
  "evaluationId": "eval-invoice-summary-0142",
  "datasetVersion": "3.0.0",
  "agentVersion": "1.2.0",
  "manifestDigest": "sha256:…",
  "policyVersion": "0.1.0",
  "metric": "correct-invoice-retrieved",
  "score": 0.70,
  "threshold": 0.90,
  "passed": false,
  "traceId": "…"
}
  • datasetVersion과 agentVersion: 어느 시험지로 어느 버전을 채점했는지를 적습니다. 둘 중 하나만 바뀌어도 다른 결과로 봅니다.
  • metric: 무엇을 쟀는지를 적습니다. 여기서는 "올바른 청구서를 가져왔는가"입니다. 금액을 잰 amount-exact-match 레코드가 하나 더 있고 그 점수는 29/40 = 0.725입니다.
  • passed: 점수가 기준 이상인지를 나타냅니다. 두 지표가 모두 통과해야 승격 후보가 됩니다.

전체 점수 옆에는 질문 유형별 점수를 항상 나란히 둡니다. 1.2.0은 번호 질문 28/28, 거래처명 질문 0/12입니다. 0.70이라는 숫자 하나로는 알 수 없던 고장의 위치가 이 두 숫자에서는 바로 보입니다.

직접 해 보기

  1. 시험지를 2.0.0으로 바꾸면 1.2.0은 몇 점인가요. 그 점수는 거래처명 질문에 대해 무엇을 말해 주나요.
  2. 시험지를 3.0.0으로 두고 금액만 채점하면 몇 행을 놓치나요.

잘못되면

시험지가 실제 질문을 닮지 않으면 만점도 소용이 없습니다. 민준의 1.2.0은 번호 질문 28행에서 만점을 받고 승인됐지만 서연의 첫 거래처명 질문에서 틀렸습니다. 고장을 먼저 발견한 사람은 사용자인 서연이었고, 그 사이 틀린 금액이 보고서에 들어갈 뻔했습니다. 그러니 운영에서 들어오는 질문 유형을 시험지에 넣고, 틀린 요청이 생기면 그대로 행으로 추가합니다.

금액만 채점하면 엉뚱한 청구서를 가져오고도 금액이 우연히 같은 행을 정답으로 셉니다. row-36이 그런 행이어서 금액 지표는 29/40으로 한 행 더 높게 나옵니다. 그래서 답이 맞았는지와 함께 어느 청구서를 가져왔는지도 채점합니다.

더 보기: 한 번만 채점할 때, 고치는 데 쓴 시험지만 볼 때, 기준을 낮출 때

한 번만 실행해 채점하면 가끔 틀리는 행을 놓칩니다. 고친 버전 1.3.0은 지시문이 길어진 뒤 번호 질문 row-09와 row-21에서 세 번 중 한 번 거래처명 형식으로 조회합니다. 세 번 모두 맞아야 정답으로 치면 37/40 = 0.925가 35/40 = 0.875로 내려가 기준에 못 미칩니다. 이야기의 게이트는 1회 기준(예시)이라 통과했고, 민준은 흔들리는 두 행을 숨기지 않고 승인 기록의 "알려진 한계"에 적었습니다. 위험도가 high인 Agent라면 반복 채점을 게이트로 삼습니다.

고치는 데 쓴 시험지의 점수를 "처음 보는 질문에서도 잘한다"는 증거로 쓰면 과신하게 됩니다. 0.925는 민준이 열어 보고 고치는 데 쓴 40행에서의 점수입니다. 그래서 민준이 열어 보지 않은 20행을 따로 남겨 두고(invoice-summary-holdout 1.0.0) 승인 직전에 한 번만 채점합니다. 1.3.0은 18/20 = 0.90이고 번호 질문 10/10, 거래처명 질문 8/10입니다.

기준을 0.70으로 낮추면 12행이 틀리는 1.2.0이 그대로 통과합니다. 위 시뮬레이터에서 기준을 바꿔 확인할 수 있습니다. 기준은 Agent마다 편한 대로 정하지 않고 evaluationProfile로 묶어 관리합니다.

채점 방식 세 가지 같은 row-33에 적용하면 이렇습니다.

방식 이 행에서 보는 것 맞는 자리
코드 채점 가져온 청구서 번호가 INV-2048인가, 금액이 12,400,000인가 정답이 하나로 정해지는 값
모델 채점 요약이 청구서 원문에 없는 내용을 지어내지 않았는가 글의 충실성처럼 규칙으로 쓰기 어려운 것
사람 채점 표본 5행을 사람이 읽고 확인 모델 채점기 자체가 맞는지 확인할 때

작은 사례 policy-search(사내 규정 검색 Agent)는 "출장비 한도가 얼마야"에 답할 때 검색된 규정 문서에 근거했는지를 재는 근거성 지표를 씁니다.

내가 할 일

  1. 운영에서 틀린 요청을 그대로 시험지의 행으로 추가합니다.
  2. 행마다 기대 답과 함께 "무엇을 가져왔어야 하는지"를 적습니다.
  3. 채점 방식을 고릅니다. 정해진 값은 코드로, 글의 품질은 모델과 사람 표본으로 봅니다.
  4. 기준을 정합니다. 전체 점수와 질문 유형별 점수를 함께 봅니다.
  5. 시험지 버전을 올리고, 운영 중인 버전을 새 시험지로 다시 채점합니다.

내 PC에서 해 보기 지금 실행되는 것은 결과 레코드의 형식 검증입니다. 저장소 루트에서 실행하면 examples/fixtures/evaluation.json을 포함한 fixture가 계약에 맞는지 확인합니다.

python -m unittest tests.test_contracts

규칙으로 정리

  • 평가는 배포 전 평가(이 장), 실행 추적 분석(Agent Observability), 운영 모니터링의 세 단계로 합니다.
  • 평가 결과는 evaluation.schema.json을 따르며 datasetVersion, agentVersion, manifestDigest, policyVersion, metric, score, threshold, passed, traceId를 포함합니다(MUST). 장면 ⑨
  • 재는 것은 품질(과제 완료, 정확성, 근거성, 도구 사용 정확성), 안전(인젝션 저항, 민감정보), 운영(지연, 비용)입니다.
  • 위험도 high Agent는 프로덕션 승인 전에 red teaming을 포함합니다(MUST).
  • 게이트를 통과한 버전은 승격 후보일 뿐이고 프로덕션 승인은 사람이 따로 합니다(수명주기와 프로덕션 승인).

한 문장으로

내보내기 전에 시험을 치르게 하고, 시험지는 실제로 들어오는 질문을 닮아야 합니다.

이해 점검

Q1. 번호 질문만 든 시험지에서 만점을 받은 버전이 있습니다. 이 점수로 알 수 없는 것은 무엇인가요?

번호가 아닌 방식으로 묻는 질문에서 어떻게 동작하는지는 알 수 없습니다. 시험지에 없는 유형은 한 번도 검사받지 않았기 때문입니다.

Q2. 금액 지표는 0.725인데 가져온 청구서 지표는 0.70입니다. 왜 다른가요?

엉뚱한 청구서를 가져왔는데 금액이 우연히 같았던 행이 하나 있기 때문입니다. 금액만 보면 그 행을 정답으로 셉니다.

Q3. 고친 버전이 0.925를 받았습니다. 이 숫자가 배포 전에 알려 주는 것과 남기는 질문은 무엇인가요?

고치는 데 쓴 40행에서 전에 틀리던 문제를 맞히고 전에 맞던 문제를 계속 맞힌다는 것을 알려 줍니다. 처음 보는 질문에서도 그런지는 따로 남겨 둔 시험지로 확인해야 합니다.

다음 장면은 ⑩입니다. 틀린 12행을 원인별로 묶어 고치고 새 버전으로 올립니다.
