Agent Observability

개발자 가이드 문서입니다. 규범은 관측성 기술 표준 문서가 기준입니다.

  1. ①호출 진입
  2. ②Agent 등록
  3. ③실행
  4. ④도구 호출
  5. ⑤권한 위임
  6. ⑥모델 호출
  7. ⑦Guardrail 검사
  8. ⑧실행 추적
  9. ⑨평가
  10. ⑩개선과 승격
  11. ⑪사용 화면

지금까지 invoice-summary는 번호로 묻는 요청 A를 잘 처리했고, 숨은 지시문이 든 요청 D도 Guardrail이 막았습니다. 며칠 뒤 서연이 번호 대신 "한빛상사 10월 청구서 요약해 줘"라고 물었습니다(요청 B).

장면

서연이 민준에게 알립니다. "한빛상사 10월 금액이 틀려요. 9,800,000원이라는데 실제는 12,400,000원이에요." 민준이 가진 단서는 서연의 화면에 찍힌 호출 번호 하나입니다. 그 번호로 추적 기록을 열어 보니 구간 네 개가 모두 성공이고 유난히 느린 곳도 없습니다. 오류는 없는데 답은 틀렸습니다. 이 장에서는 이 기록으로 어디까지 알 수 있고 어디부터는 알 수 없는지를 봅니다.

Agent Observability가 없다면 서연의 신고를 받고도 그 요청이 어디를 거쳤는지 찾을 방법이 없습니다.

무슨 일이 일어나나

  1. 1. 번호로 기록을 찾는다invocationId · traceparent
  2. 2. 구간별 시간과 성공 여부를 본다span 트리
  3. 3. 오류가 없으면 범위를 좁힌다남은 가설 둘
  4. 4. 다시 실행해 원인을 확인한다개발 환경

실물 보기

요청 B의 추적 기록입니다. 구간 하나를 span이라고 부릅니다.

예시

invoke_agent invoice-summary          1,840ms  성공
├─ chat (검색어 만들기)                  320ms  성공
├─ execute_tool tool-erp-read           210ms  성공   결과 1건
└─ chat (요약 만들기)                  1,160ms  성공
  • 네 줄의 추적 번호가 같아서 한 요청의 일로 묶여 보입니다.
  • 결과 1건: 도구가 청구서 하나를 돌려줬다는 것까지만 남습니다. 어느 청구서였는지는 없습니다.
  • 고장은 첫째 chat에서 났습니다. 모델이 검색어(query)를 "한빛상사"로만 만들어 월이 빠졌습니다. 그런데 모델은 오류 없이 답을 냈기 때문에 기록에는 성공으로만 보입니다.

내 PC의 로컬 mock이 요청 A 한 번에 실제로 남기는 감사 기록 다섯 줄입니다.

  • 다섯 줄의 traceparent가 같습니다. Agent Platform APIs, Runtime, Credential Broker, 도구 경로, 모델 경로가 한 요청의 일로 묶입니다.
  • 어느 테넌트의 어느 호출이(tenantId, invocationId), 어떤 정책 결정으로(decisionId), 어떤 도구와 모델 쪽을(toolId, provider) 썼는지가 남습니다.
  • 질문 문장, 검색어, 도구가 돌려준 내용은 어느 줄에도 없습니다. 기밀이 로그로 새는 경로를 만들지 않으려고 일부러 남기지 않습니다.

그래서 추적 기록으로는 원인을 확정할 수 없고 범위를 좁힐 수 있습니다. 요청 B에서 기록으로 배제한 가설은 "네트워크, 정책, 도구 오류"이고, 남는 가설은 둘입니다. 조회가 엉뚱한 청구서를 가져왔거나, 조회는 맞았는데 요약이 금액을 틀렸거나입니다. 민준은 개발 환경에서 같은 질문을 다시 실행해 기대한 INV-2048 대신 INV-2101이 조회된 것을 보고, 검색어에 월이 빠진 것을 확인합니다.

직접 해 보기

  1. 오류가 없는데 답이 틀렸습니다. 구간을 눌러 남은 속성을 본 뒤 다음에 할 일을 골라 보세요.
  2. 추적 번호 전달을 끊으면 기록이 어떻게 보이나요.

잘못되면

하위 Agent를 부르면서 추적 번호를 넘기지 않으면 기록이 두 동강 납니다. 출장 정산 Agent expense-settlement가 invoice-summary를 부르는 경우, 민준이 traceparent를 넘기지 않으면 하위 Agent의 구간은 새 번호로 기록됩니다. 신고를 받은 사람은 위쪽 한 줄만 보게 되고 그 아래에서 무슨 일이 있었는지 따라갈 수 없습니다. 직접 HTTP로 부르지 않고 플랫폼의 ctx로 부르면 번호는 자동으로 이어집니다.

디버깅이 편하다고 프롬프트 원문을 로그에 남기면 기밀이 로그로 새는 길이 생깁니다. 청구서 내용은 confidential인데 로그 저장소는 그만큼 엄격하게 보호되지 않는 경우가 많습니다. 그러면 청구서를 볼 권한이 없는 사람도 로그에서 청구서 내용을 보게 됩니다. 원문이 필요하면 개발 환경에서 합성 데이터로 다시 실행합니다.

더 보기: 지표만 볼 때, 호출 번호를 보여 주지 않을 때

지표만 보고 추적을 보지 않으면 요청 B 같은 고장은 보이지 않습니다. 오류율은 0%이고 평균 지연도 정상이기 때문입니다. 틀린 답은 지표가 아니라 사용자 신고와 평가(Agent Evaluation)로 잡습니다.

호출 번호를 사용자에게 보여 주지 않으면 서연의 신고를 받고도 수많은 요청 가운데 어느 것인지 찾지 못합니다. 앱은 응답의 invocationId를 화면이나 오류 메시지에 함께 보여 줍니다.

내가 할 일

  1. 신고를 받으면 호출 번호로 추적 기록을 찾습니다.
  2. 오류가 난 구간이나 가장 긴 구간을 먼저 봅니다.
  3. 오류가 없으면 남은 가설을 적고, 같은 질문을 개발 환경에서 다시 실행합니다.
  4. 원인을 찾았으면 틀린 요청을 평가 데이터셋의 행으로 추가합니다. 이 일은 다음 장에서 이어집니다.

내 PC에서 해 보기 Agent Tools의 요청을 다시 보내고 응답의 traceparent를 확인합니다. 가운데 32자리가 추적 번호입니다.

make scenarios는 시나리오마다 추적 번호와, 같은 번호로 서비스별로 남은 감사 기록을 출력합니다. 로컬 mock 모델은 검색어를 만들지 않으므로 내 PC에서는 "월 누락"이 재현되지 않습니다. 민준이 다시 실행해 확인하는 대목은 이야기 속에서만 일어납니다.

한 문장으로

요청 하나가 어디를 거쳤고 어디서 얼마나 걸렸는지 번호 하나로 따라갑니다.

이해 점검

Q1. 도구가 1건을 돌려줬다는 기록으로 어떤 청구서를 가져왔는지 알 수 있나요?

알 수 없습니다. 추적 기록은 조회 인자와 결과의 원문을 남기지 않습니다. 개발 환경에서 같은 질문을 다시 실행해 확인합니다.

Q2. 요청 B의 기록은 네 구간 모두 성공입니다. 이 사실이 지워 주는 가설과 남기는 가설은 무엇인가요?

네트워크, 정책, 도구 고장은 지워집니다. "조회가 엉뚱한 청구서를 가져왔다"와 "요약이 금액을 틀렸다"가 남습니다.

Q3. 민준이 디버깅용으로 프롬프트 원문을 로그에 남기려 합니다. 무엇이 문제인가요?

기밀인 청구서 내용이 로그 저장소로 복사됩니다. 그러면 원본을 볼 권한이 없는 사람도 로그에서 그 내용을 보게 됩니다.
