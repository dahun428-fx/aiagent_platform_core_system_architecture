Agent Tools

개발자 가이드 문서입니다. 규범은 Agent Tools, Agent Identity, Durable / HITL 기술 표준 문서가 기준입니다.

  1. ①부른다
  2. ②어떻게 여기 있나
  3. ③실행된다
  4. ④ERP를 읽고 메일을 보내려 한다
  5. ⑤누구 권한으로
  6. ⑥모델에 묻는다
  7. ⑦함정을 만난다
  8. ⑧답이 틀렸다
  9. ⑨점수를 매긴다
  10. ⑩고쳐서 다시 올린다
  11. ⑪어디서 이 일을 하나

지금까지 서연이 "청구서 INV-2048 요약해 줘"를 보냈습니다. Agent Platform APIs가 서연을 확인했고, 민준이 등록한 invoice-summary의 코드가 실행되기 시작했습니다.

설명

장면

민준의 코드는 이제 ERP에서 청구서를 읽어 와야 합니다. 그런데 코드 어디에도 ERP 주소나 API 키가 없고, Manifest에 tool-erp-read라는 이름 하나만 적혀 있습니다. 잠시 뒤 서연이 "이 요약을 한빛상사 담당자에게 메일로 보내 줘"라고 합니다. 보내는 일은 다른 Agent인 invoice-mailer가 맡는데, 메일은 바로 나가지 않고 재무팀장 지훈의 승인을 기다립니다. 이 장에서는 읽기는 바로 되는데 보내기는 왜 멈추는지를 봅니다.

Agent Tools가 없다면 Agent마다 ERP 비밀번호를 들고 다니고, 메일은 누구의 확인도 없이 나갑니다.

무슨 일이 일어나나

  1. 1. 이름과 검색어를 넘긴다Agent 코드
    주소·자격증명 없음
  2. 2. 써도 되는 도구인지 본다Agent Gateway 도구 경로
  3. 3. 플랫폼이 ERP를 대신 호출한다Credential Broker의 lease
  4. 4. 결과만 돌아온다청구서 내용
  5. 5. 보내는 일은 승인까지 멈춘다쓰기 도구 + 사람 승인

실물 보기

Agent가 도구를 부르는 코드 한 줄입니다.

예시

found = ctx.call_tool("tool-erp-read", "1.0.0", {"query": "INV-2048"})
  • "tool-erp-read": 주소가 아니라 이름입니다. 주소와 자격증명은 플랫폼만 압니다.
  • "1.0.0": 도구에도 버전이 있어서, 도구가 바뀌어도 Agent가 모르는 사이에 동작이 달라지지 않습니다.
  • {"query": ...}: 도구가 받겠다고 선언한 인자만 보낼 수 있으므로 주소를 넣을 자리가 없습니다.

플랫폼이 이 이름으로 찾아보는 도구 등록 정보(descriptor)입니다. 저장소의 examples/fixtures/tool-descriptor.json과 같은 필드입니다.

예시

{
  "toolId": "tool-erp-read",
  "version": "1.0.0",
  "protocol": "rest-openapi",
  "effect": "read",
  "allowedScopes": ["tools.read"],
  "inputSchema": "…/tool-input.schema.json",
  "outputSchema": "…/tool-output.schema.json"
}
  • effect: read는 읽기만 합니다. 메일 도구 tool-mail-send는 여기가 write이고, write인 도구는 승인이 있어야 실행됩니다.
  • allowedScopes: 이 도구를 쓰려면 호출자에게 있어야 하는 권한입니다. 서연에게 tools.read가 있어서 조회가 됩니다.
  • inputSchema, outputSchema: 들어가는 값과 나오는 값의 형식입니다. 형식에 맞지 않으면 ERP까지 가지 않습니다.
더 보기: 도구 경로가 실제로 받는 요청과 돌려주는 결과

Agent 코드의 한 줄이 도구 경로에 도착할 때는 플랫폼이 신원과 정책 정보를 덧붙인 모습입니다. 로컬 fixture examples/fixtures/tool-invoke.json의 발췌입니다.

실행 결과 · 내 PC의 로컬 mock

{
  "invocationId": "inv-demo",
  "toolId": "tool-search",
  "version": "0.1.0",
  "arguments": {"query": "hello"},
  "identity": {"tenantId": "tenant-demo", "mode": "delegated", "principalId": "user-demo", "scopes": ["tools.read", "agents.invoke", "models.invoke"]},
  "policy": {"decisionId": "policy-demo", "allowed": true, "allowedResources": ["tool-search", "model-self-hosted", "model-external"]},
  "idempotencyKey": "fixture-tool"
}

identity, policy, idempotencyKey는 Agent 코드가 적은 것이 아니라 Runtime이 붙인 것입니다. 결과(tool-result.json)에는 status와 output만 있고 자격증명은 없습니다.

{"invocationId": "inv-demo", "toolId": "tool-search", "status": "succeeded", "output": {"content": "tool:hello"}}

직접 해 보기

  1. 코드에서 Manifest에 없는 도구를 불러 보세요. 이것은 등록 실패인가요, 등록한 코드가 실행 중에 거절된 것인가요.
  2. 쓰기 도구에 다른 요청에서 받은 승인을 붙여 보세요. 앱은 무엇을 받나요. 승인이 아예 없을 때와 구별할 수 있나요.

잘못되면

민준의 코드가 Manifest에 적지 않은 도구를 부르면 서연의 요청은 실행 중에 403을 받습니다. 로컬 mock의 응답 본문에는 Tool is not declared in the Agent Manifest라고 적혀 있습니다. Manifest가 유효했고 등록도 됐고 코드까지 실행된 뒤에 나는 실패입니다. capabilities.tools에 도구 이름을 추가하고 새 버전으로 등록하면 고쳐집니다. 도구 목록을 아예 비운 Manifest는 여기까지 오지 못하고 등록 전 검증에서 멈춥니다(Agent Factory와 Manifest).

승인이 붙지 않은 채 메일 도구를 부르면 앱은 403 Policy denied를 받습니다. 평소에는 플랫폼이 승인까지 실행을 멈춰 주지만, 어떤 이유로든 승인 없는 호출이 도구 앞까지 오면 도구 경로가 마지막으로 거절합니다. 운영자가 도구 경로를 직접 보면 이유가 Write tool requires approval로 적혀 있습니다. 코드를 고쳐서 풀 일이 아니고, 승인자가 승인해야 풀립니다.

더 보기: 앱에서는 같아 보이는 거절 셋, 그리고 응답이 끊겼을 때
상황 앱이 받은 응답 도구 경로의 내부 진단 참조 구현 시나리오
등록되지 않은 도구를 부름 403 Policy denied Tool not approved S5 tool-not-approved
승인 없이 쓰기 도구를 부름 403 Policy denied Write tool requires approval S6a write-no-approval
만료됐거나 다른 요청의 승인을 붙임 403 Policy denied Approval is stale or not bound to this request S6a write-approval-expired, write-approval-other-request
메일 서버의 응답이 오다가 끊김 실패 응답 unknown_outcome S6a write-response-lost
다시 실행할 때 같은 키에 다른 인자가 실림 409 CONFLICT 같은 키, 다른 내용 S5 tool-key-conflict

앞의 셋은 앱에서 모두 같은 Policy denied로 보입니다. 거절 이유를 바깥에 자세히 알려 주면 공격자에게도 알려 주는 셈이라 일부러 구분하지 않습니다. 어느 경우인지는 호출 번호(invocationId)로 운영자에게 묻습니다.

unknown_outcome은 메일이 나갔는지 알 수 없는 상태입니다. 자동으로 다시 보내면 두 번 나갈 수 있으므로 다시 보내지 않고 메일 서버의 기록과 대조합니다. 도구 호출의 멱등성 키는 Agent 코드가 아니라 Runtime이 붙입니다.

Agent가 주소를 직접 넘기는 길은 계약에 없습니다. 그런 길이 있다면 문서에 숨은 지시문이 Agent를 시켜 http://10.0.0.5/admin 같은 사내망 주소를 찔러 볼 수 있기 때문입니다.

내가 할 일

  1. 쓸 도구의 ID와 버전을 확인합니다.
  2. Manifest의 capabilities.tools에 그 ID를 적고, identity.requiredScopes에 도구가 요구하는 scope를 적습니다.
  3. 코드에서 ctx.call_tool(도구 ID, 버전, 인자)로 부릅니다. 주소와 키는 넣지 않습니다.
  4. 로컬에서 실행해 보고 적합성 검사의 C8(선언하지 않은 도구, 자격증명 노출)을 확인합니다.
  5. 쓰기 도구가 필요하면 읽기 Agent에 덧붙이지 말고 별도 Agent로 나눕니다.

규칙으로 정리

  • Agent는 도구의 ID, 버전, 인자만 넘깁니다. 주소와 자격증명은 넘길 수 없습니다(MUST NOT). 장면 ④
  • Manifest의 capabilities.tools에 없는 도구 호출은 거절합니다(MUST). 장면 ④
  • 쓰기 도구는 그 요청에 묶인 유효한 승인이 있어야 실행합니다(MUST). 장면 ④ 뒷부분
  • 쓰기의 성공 여부를 알 수 없으면 자동으로 다시 실행하지 않고 unknown_outcome으로 기록합니다(MUST).
  • MCP 서버는 도구를 제공하는 방식 가운데 하나이며 같은 도구 경로를 지납니다. 토큰을 그대로 넘겨주는 방식(token passthrough)은 쓰지 않습니다(MUST NOT).

조각 2 / 10. 색이 채워진 조각이 지금까지 붙인 것이고, 점선은 아직 붙이지 않은 조각입니다.

도구 경로가 없을 때

Agent Platform APIs까지 붙인 Agent의 코드입니다.

ERP_PASSWORD = "erp-s3cret"


def handle(content):
    invoice_id = re.search(r"INV-\d+", content).group()
    invoice = world.erp_read(ERP_PASSWORD, invoice_id)
    return world.model(f"{invoice['vendor']} {invoice['amount']:,}원, 납기 {invoice['due']}")

첫 줄 때문에 세 가지 일이 생깁니다. 비밀번호가 코드와 함께 저장소에 올라가므로 저장소를 볼 수 있는 사람은 누구나 ERP에 들어갈 수 있습니다. ERP 비밀번호를 바꾸는 날에는 이 값을 적어 둔 Agent를 전부 찾아 고쳐서 다시 배포해야 합니다. 그리고 비밀번호를 가진 코드는 ERP에서 무엇이든 할 수 있어서, 청구서 읽기만 하겠다던 Agent가 내일 송금 API를 불러도 막을 곳이 없습니다.

도구 경로가 하는 일

비밀번호를 Agent에서 플랫폼으로 옮기고, Agent는 도구의 이름만 넘기게 합니다. Agent가 부를 수 있는 이름은 Manifest에 미리 적어 둡니다.

예시

{"id": "invoice-summary", "tools": ["tool-erp-read"]}

도구_호출(도구 이름, 인자):
    이 Agent의 Manifest에 없는 이름이면
        거절한다                              # 신청하지 않은 도구는 부를 수 없다
    보관소에서 그 도구의 비밀번호를 꺼낸다    # Agent는 이 값을 보지 못한다
    플랫폼이 도구를 대신 부른다
    결과만 Agent에게 돌려준다

코드로 옮기면 mini_platform.py에 다음이 더해집니다.

예시

# examples/build/step2/mini_platform.py 에 새로 생긴 부분
# ① 비밀번호는 플랫폼이 가진다
VAULT = {"erp": world.ERP_PASSWORD}
# ② 이름과 실제로 할 일의 짝
TOOLS = {"tool-erp-read": lambda args: world.erp_read(VAULT["erp"], args["invoice_id"])}
MANIFEST = json.loads((Path(__file__).parent / "manifest.json").read_text(encoding="utf-8"))


class Context:
    """Agent가 플랫폼에 부탁할 수 있는 일의 전부입니다."""

    def call_tool(self, tool_id, args):
        # ③ Manifest에 없는 이름은 거절한다
        if tool_id not in MANIFEST["tools"]:
            raise PermissionError(tool_id + "는 Manifest에 없는 도구입니다")
        # ④ 플랫폼이 대신 부른다
        call = TOOLS[tool_id]
        return call(args)
  • ① 비밀번호가 사는 곳이 Agent 파일에서 플랫폼의 VAULT로 옮겨졌습니다. 이제 비밀번호를 바꿀 때 고칠 곳은 여기 한 곳입니다.
  • ② 도구 하나는 "이름과, 그 이름으로 실제로 할 일"의 짝입니다. 비밀번호를 꺼내 ERP를 부르는 코드가 이 안에 있으므로, 이름만 아는 쪽은 비밀번호를 만질 일이 없습니다.
  • ③ 실제 호출보다 먼저 Manifest를 봅니다. 이름이 없으면 ④까지 가지 못하므로 ERP에는 아무 요청도 나가지 않습니다.
  • ④ Manifest에 있는 이름만 여기까지 옵니다. 돌려주는 것은 ERP의 응답뿐이고 VAULT의 값은 Context 밖으로 나가지 않습니다.

enter()는 한 줄만 바뀝니다. Agent를 호출할 때 Context 객체를 함께 넘깁니다.

-    result = {"status": 200, "output": agent.handle(request["content"])}
+    result = {"status": 200, "output": agent.handle(Context(), request["content"])}

호출 두 개가 지나가는 모습

호출 끝나는 곳 결과 ERP에 나간 요청
ctx.call_tool("tool-erp-read", {"invoice_id": "INV-2048"}) ④ {'vendor': '한빛상사', 'amount': 12400000, 'due': '2026-11-30'} 1건
ctx.call_tool("tool-mail-send", {}) ③ PermissionError: tool-mail-send는 Manifest에 없는 도구입니다 없음

두 번째 행에서 tool-mail-send라는 도구가 플랫폼에 있는지 없는지는 따지지도 않았습니다. Manifest에 없다는 이유만으로 먼저 거절됩니다.

실제 플랫폼과의 대응

이 코드 실제 플랫폼
TOOLS Tool Registry. 도구의 이름, 버전, 읽기·쓰기 구분을 등록합니다
VAULT Credential Broker. 비밀번호 대신 이 호출에만 묶인 lease(실제 자격증명을 가리키는 불투명 참조)를 발급합니다
Context.call_tool Agent Gateway의 도구 경로. 호출마다 정책을 확인하고 기록합니다
manifest.json Agent Manifest의 capabilities.tools
PermissionError 403

남은 FAIL 두 줄이 다음에 붙일 조각입니다. 검사 5는 같은 Agent를 불러도 사람에 따라 결과가 달라야 한다는 것이고(Agent Identity), 검사 6은 모델도 도구처럼 플랫폼을 거쳐 불러야 한다는 것입니다(Agent Gateway).

한 문장으로

Agent는 도구의 이름만 알고, 주소와 비밀번호는 플랫폼이 쥐고 대신 불러 줍니다.

이해 점검

Q1. 민준의 코드가 Manifest에 적지 않은 tool-mail-send를 부릅니다. 등록은 통과했습니다. 서연이 요청을 보내면 어떻게 되나요?

코드는 실행되지만 그 도구를 부르는 순간 403으로 거절됩니다. 등록에 실패한 것이 아니라 실행 중에 거절된 것이므로, Manifest에 도구를 추가해 새 버전으로 등록해야 합니다.

Q2. 서연의 앱이 403 Policy denied를 받았습니다. 승인이 없어서인지 승인이 만료돼서인지 앱이 구별할 수 있나요?

앱이 받는 응답이 같아서 구별할 수 없습니다. 호출 번호를 전달하면 운영자가 도구 경로의 기록에서 이유를 확인합니다.

Q3. 메일 도구를 부른 뒤 응답이 끊겼습니다. Agent가 한 번 더 보내면 안 되는 이유는 무엇인가요?

메일이 이미 나갔을 수 있기 때문입니다. 성공했는지 알 수 없는 쓰기는 다시 실행하지 않고 대상 시스템의 기록과 대조해 확정합니다.

다음 장면은 ⑤입니다. 같은 Agent인데 왜 서연이 부르면 되고 인턴 하준이 부르면 안 되는지를 봅니다.
