# Agent Tuning

> 개발자 가이드 문서입니다. 규범은 [Agent Tuning](../agent-tuning.md), [평가](../evaluation.md) 기술 표준 문서가 기준입니다.

{{journey:10}}

<div class="sofar" markdown="1">
**지금까지** 민준이 거래처명으로 묻는 질문 12행을 평가 데이터셋에 더해 `3.0.0`을 만들었습니다. 운영 중인 `invoice-summary 1.2.0`을 다시 채점하니 28/40 = 0.70으로, 기준 0.90에 못 미쳤습니다.
</div>

## 장면

민준은 틀린 12행을 하나씩 열어 봅니다. "한빛상사 10월 청구서"를 "한빛상사"로 조회한 행, "대성물산 9월 청구서"를 "대성물산"으로 조회한 행이 이어집니다. 원인별로 묶어 보니 9행은 검색어(query)에서 월이 빠졌다는 같은 이유로 틀렸습니다. 민준은 지시문에 두 문장을 더해 같은 평가 데이터셋으로 다시 채점하고, 운영 중인 버전은 건드리지 않은 채 새 버전 `1.3.0`으로 올립니다.

<div class="point" markdown="1">
**{{icon:bulb}} Agent Tuning이 없다면** 고친 사람의 "이제 될 거예요"가 유일한 근거가 되고, 고치다가 전에 되던 것을 망가뜨려도 운영에서야 압니다.
</div>

## 실물 보기

민준이 만든 실패 분류표입니다.

<!-- kind: example -->

| 원인 | 행 수 | 예 | 해당 행 |
|---|---|---|---|
| 월 누락 | 9 | "한빛상사 10월 청구서"를 `한빛상사`로 조회 | `row-31`~`row-39` |
| 거래처 약칭 | 2 | "한빛 10월 청구서"를 `한빛`으로 조회해 0건 | `row-29`, `row-30` |
| 상대 날짜 | 1 | "지난달 청구서"의 "지난달"을 날짜로 바꾸지 못함 | `row-40` |

- 세 가지를 한꺼번에 고치면 무엇이 효과가 있었는지 알 수 없으므로 가장 큰 묶음 하나만 고릅니다.

지시문을 고친 내용입니다. 지시문은 Agent 소스 안의 `instructions.md`에 있습니다.

<!-- kind: example -->

```diff
- 청구서 번호로 `tool-erp-read`를 조회한다.
+ 청구서 번호로 `tool-erp-read`를 조회한다.
+ 번호를 모르면 `거래처명 YYYY-MM` 형식으로 조회한다.
+ 거래처명만 보내지 않는다.
```

- 코드와 함께 커밋되는 파일이라 고치면 Manifest의 `revision`(커밋 SHA)과 산출물 digest가 바뀝니다. 그래서 지시문 두 문장만 바꿔도 새 버전입니다.
- `1.2.0`과 `1.3.0`의 차이는 이 두 줄뿐입니다.

같은 평가 데이터셋 `3.0.0`으로 다시 채점한 결과입니다.

<!-- kind: example -->

| | 전체 | 번호 질문 | 거래처명 질문 |
|---|---|---|---|
| `1.2.0` | 28/40 = 0.70 | 28/28 | 0/12 |
| `1.3.0` | 37/40 = 0.925 | 28/28 | 9/12 |

- 번호 질문이 28/28 그대로이므로 전에 맞던 문제를 틀리지 않는다는 것을 확인할 수 있습니다.
- 남은 3행(`row-29`, `row-30`, `row-40`)은 다음에 고칠 대상으로 둡니다.

## 잘못되면

**과하게 고치면** 전에 되던 것이 망가집니다. 민준이 지시문을 "항상 거래처명과 월로 조회한다"로 바꿨다면(수단 나) 월 누락 9행은 맞지만, 번호로 묻는 질문에서도 번호 대신 거래처명을 찾으려다 6행이 새로 틀려 31/40 = 0.775가 됩니다. 같은 평가 데이터셋으로 다시 채점하지 않았다면 이번에도 운영에서 서연이 먼저 알아챘을 것입니다.

**운영 중인 `1.2.0`을 직접 고쳐 덮어쓰면** 어제 서연의 요청을 처리한 것이 고치기 전인지 후인지 알 수 없게 되고, 새 지시문에 문제가 있어도 되돌릴 곳이 없습니다. 그래서 개선 결과는 항상 새 버전으로 등록하고, 이전 버전은 Registry에 그대로 남깁니다.

<details class="more" markdown="1"><summary>더 보기: 비싼 수단부터 쓸 때, 승인을 건너뛸 때, 기밀을 학습에 쓸 때</summary>

| 수단 | 결과 (평가 데이터셋 `3.0.0`) | 비용 |
|---|---|---|
| 가. 지시문에 두 문장 추가 | 37/40 = 0.925 | 변화 없음, 하루 |
| 나. 지시문을 "항상 거래처명과 월로 조회"로 변경 | 31/40 = 0.775, 게이트 차단 | 변화 없음 |
| 다. 더 큰 모델로 교체 | 30/40 = 0.75, 게이트 차단 | 호출당 3배 |
| 라. 미세조정 | 정의 단계 | 가장 큼 |

**비싼 수단부터 쓰면** 돈을 쓰고도 고쳐지지 않습니다. 원인이 모델의 능력이 아니라 지시문에 있었기 때문에 수단 다는 월 누락 9행 가운데 2행만 고쳤습니다.

**"지시문만 고쳤으니 승인은 건너뛰자"** 는 통하지 않습니다. 개선 흐름은 평가와 등록을 빠르게 해 줄 뿐 프로덕션 승인 요건을 줄이지 않습니다([수명주기와 프로덕션 승인](06-lifecycle.md)).

**기밀 추적 원문을 외부 미세조정 서비스에 올리면** 데이터 반출입니다. 미세조정 데이터는 데이터 분류와 반출 정책을 따르고, 외부 튜닝 서비스도 Agent Gateway의 모델 경로 정책을 지납니다.
</details>

## 내가 할 일

1. 평가에서 틀린 행과 운영에서 신고된 요청을 모읍니다.
2. 원인별로 묶고 가장 큰 묶음 하나를 고릅니다.
3. 지시문, 도구 구성, 모델 선택, 미세조정 순서로 싼 수단부터 시도합니다.
4. 같은 평가 데이터셋으로 다시 채점하고, 전체 점수와 함께 전에 맞던 유형의 점수를 확인합니다.
5. 새 버전으로 등록하고 승인 절차를 밟습니다.

**지금 할 수 있는 일** 이 장의 흐름은 정의 단계라 실행할 명령이 없습니다. 그래도 틀린 요청의 호출 번호와 질문 유형은 지금부터 기록해 둘 수 있고, 그 기록이 평가 데이터셋의 다음 행이 됩니다.

<div class="scope" markdown="1">
**제공 범위 (v0.1)**

| 항목 | 등급 | 확인하는 곳 |
|---|---|---|

## 규칙으로 정리

| 개선 대상 | 예 | 산출물 |
|---|---|---|
| 프롬프트·지시문 | 시스템 지시문, few-shot 예시 | 새 Agent 버전 |
| 도구·검색 구성 | 도구 선택, 검색 파라미터 | 새 Agent 버전 또는 Manifest 변경 |
| 모델 선택 | 논리 모델 capability 변경 | Manifest 변경 |
| 미세조정(fine-tuning) | 평가 데이터 기반 모델 조정 | Agent Gateway 모델 경로에 새 endpoint 등록 |

- Tuning 결과는 항상 새 불변 버전으로 등록하고 기존 버전을 덮어쓰지 않습니다(MUST). 장면 ⑩
- 개선 흐름은 프로덕션 승인 요건을 줄이지 않습니다(MUST NOT).
- 미세조정 데이터는 데이터 분류와 반출 정책을 따르고, 외부 튜닝 서비스에도 모델 경로 정책을 적용합니다(MUST).

## 한 문장으로

틀린 문제를 이유별로 묶어 가장 큰 묶음부터 고치고, 같은 평가 데이터셋으로 다시 채점한 뒤 새 버전으로 올립니다.

<div class="check" markdown="1">
**{{icon:question}} 이해 점검**

<details markdown="1"><summary>Q1. 고친 버전이 전에 맞던 문제를 틀리지 않는다는 것을 어떻게 아나요?</summary>
고치기 전과 같은 평가 데이터셋으로 다시 채점해 전에 맞던 유형(번호 질문 28행)의 점수가 그대로인지 봅니다.
</details>

<details markdown="1"><summary>Q2. 민준이 더 큰 모델로 바꿨더니 비용은 3배가 됐는데 0.75가 나왔습니다. 무엇을 먼저 했어야 하나요?</summary>
틀린 행을 원인별로 묶어 보는 일을 먼저 했어야 합니다. 가장 큰 원인이 지시문에 있었으므로 지시문을 고치는 쪽이 가장 싸고 효과도 컸습니다.
</details>

<details markdown="1"><summary>Q3. 지시문 두 문장만 고쳤습니다. 운영 중인 1.2.0에 바로 반영하면 안 되는 이유는 무엇인가요?</summary>
어떤 요청이 어느 지시문으로 처리됐는지 알 수 없게 되고, 문제가 생겨도 되돌릴 버전이 없어지기 때문입니다. 지시문이 바뀌면 revision과 digest가 바뀌므로 새 버전입니다.
</details>

`1.3.0`은 승격 후보가 됐고, 프로덕션에 올리려면 지훈의 승인이 남았습니다. [수명주기와 프로덕션 승인](06-lifecycle.md)에서 승인 기록 한 장을 봅니다.
